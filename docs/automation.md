# 自動設備管理（#23）

「自動設備管理」を取得すると、表示中と最大24時間の放置中に同じ方針で設備を購入できます。**豊かな収穫ランク1・累計転生1回以上・1pt**で恒久解禁します。取得だけでは購入せず、初期の全体設定はOFFです。転生・限界突破・研究は手動のままで、自動処理は現在の上限段階を変更しません。

## 設定と購入順

設備欄の折り畳み「自動購入」で、全体ON/OFF・方針・設備別ON/OFF・指定優先順を変更します。設備別の初期設定は全7種ON、全体OFFです。未解禁設備は設定を保持したまま購入候補から除外します。優先順は全設備IDの順列で、UIで別設備を選ぶと元の位置と入れ替えます。

| 方針 | 次の購入対象 | 貯蓄と同率の扱い |
| --- | --- | --- |
| 均等 | 有効・解禁済み設備のうち所有台数が最少 | 対象が買えるまで貯める。同数は定義の掲載順 |
| 収穫効率優先（初期値） | 次の価格÷実際の生産増分が最小 | 対象が買えるまで貯める。同率は掲載順 |
| 指定設備優先 | 買える設備のうち指定順が先 | 買えない設備は即フォールバック。資金保留なし。全部買えなければ最も早く買える価格まで待つ。同価格は指定順 |

掲載順は `worker / cart / harvester / deepDrill / refinery / veinExtractor / concentrator` です。均等の台数には手動購入分も含めます。均等と収穫効率は現在買える設備だけから選ばず、残高に依存しない次の目標を決めます。これによりタイマーの小分け回数で購入計画を変えません。特定設備を除外したければ個別設定をOFFにしてください。

収穫効率は `getEquipmentPurchaseGain` を使い、9→10 / 24→25 / 49→50で所有済み設備全体に乗る倍率の増分も含めます。価格・割引・各台の切上げ・最終購入可否は既存の価格/購入APIに委譲し、独自の価格式を持ちません。指定順の変更は将来の設備を優先する場合にも使えますが、未解禁設備は購入しません。

## 経過時間の精算

`advanceGame` は `advanceWithAutomation` の状態を返します。後者は自動購入台数、上限到達までの秒数、任意の購入イベント列も返します。次の処理を繰り返します。

1. 現在の上限に到達していれば停止。上限と購入が同時なら上限を先に処理し、追加購入しない。
2. 現在買える対象なら1台購入し、生産力・次の価格・次の目標を再計算する。
3. 次の購入可能時刻・上限到達時刻・残り時間のうち最短の境界まで収穫する。
4. 残り時間だけを次の区間に使う。購入イベント後の生産増加を、それ以前の時間に適用しない。

収穫後にまとめて買う方式や、秒・ミリ秒ごとの固定ループは使いません。OFFまたは対象なしでは従来の定率収穫へ進みます。手動操作・設定変更の直前には、旧設定でその時刻までを精算します。設定ONの瞬間は経過0秒で既存資金から買える分を購入し、OFFはその後の購入を停止します。候補設定・即時購入を保存できた場合だけ適用するため、書込失敗で設定や残高を失いません。

### 数値精度と負荷

現在はGameNumberで全収穫を補償加算し、周回の `productionRemainder` に丸め端数を保持します。v5/v6の `automationRemainder` も符号付きで移行し、転生でゼロへ戻します。

価格未満の残高を価格へ引き上げる微小信用補正は#28で撤去しました。正規化された残高と価格を直接比較し、端数は次の実収穫で相殺します。上限優先、0.37秒×約23万回と24h一括の購入一致、有限の端数範囲、分解能不足時の安全停止を検証します。詳細な契約・許容誤差は [巨大数移行](number-migration.md)。

計算量は購入イベント数E・設備数kに対して概ね `O(E × k log k)`、現在k=11です。時刻の長さや描画回数には比例しません。#31の上限1e18に合わせ、1回の精算の上限を2,048購入・内部16,384イベントへ拡張しました。超過時は例外として部分結果を適用せず、セッションを停止・元セーブを保護します。通常のUI精算ではイベント列を保持せず、シミュレーターだけ記録します。[根源領域の精度・負荷](origin.md) を参照してください。

#23時点のnumber版ではNode24/Windowsで、24ケースをウォームアップ後に4回測定した96精算の中央値は約2.0ms・最大約7.2ms、最大160購入でした。残高約1e9・全設備0台・最大の有限経過時間というストレス状態も約4.9ms・158購入で1e9に停止しました。端末差があるため時間は参考値ですが、24時間分の固定刻み処理を行っていないことも購入イベント数で確認できます。

## 保存とUI

自動購入はv5で導入し、現在の保存はv12です。設定 `automation` は周回リセット対象と分け、通常転生・突破で維持します。スキルは `permanent.skillRanks.automation` に保存します。v1〜v4は既存の残高・設備・恒久データ・上限段階を保持し、自動スキル0・全体OFFの既定設定を補います。v4の突破済み1e9データも保持します。v2〜v4の非ゼロ自動スキルは拒否し、v1の恒久データは採用しません。v5の全5スキルと旧5設備設定を保持し、v6では新設備の個別ONを補い、優先順末尾に追加します。全体OFFは維持します。段階2未満で新設備は買わず、研究・研究強化・突破は自動実行しません。詳細は [保存仕様](save.md)。

不正な方針、欠けた/未知の設備ID、重複・欠落した優先順、非booleanのON/OFF、権利なしON、異常な補償端数を拒否します。破損・未対応形式・移行後の書込失敗では元テキストを保持します。既存の確認付きインポート/エクスポート・複数タブ検知・24時間上限を維持し、インポート時の追加放置報酬はありません。

直近の購入台数はセッションで最後に自動購入が起きた精算の合計です。購入がない更新で消さず、毎購入の読み上げ・達成通知は行いません。読込時は放置報告の購入数を使い、手動インポート/初期化で通知をリセットします。放置報告の「獲得芋」は設備支出前の収穫量です。自動購入は10秒ごとの自動保存・ページ離脱時に保存され、設定変更と手動購入は即保存します。保存前に閉じても保存時刻から同じ自動計算を再実行できます。

## 採用コストと成長比較

自動設備管理は任意の1ptで、従来の突破だけの経路（前提込み10pt・5回転生）は維持します。先に自動設備管理を買う経路は計11ptとなり上限転生6回が必要ですが、低頻度での権利取得時刻は短縮しました。既存スキル・設備・突破条件は変更していません。

| 確認間隔 | 自動購入 | 突破権取得 | 突破時刻 | 突破後1e9まで | 開始からの総時間 |
| --- | --- | ---: | ---: | ---: | ---: |
| 1分 | OFF・確認時に手動 | 43分 | 50分 | 3時間40分 | 4時間30分 |
| 1分 | 均等 / 収穫効率 | 39分 | 43分 | 1時間27分 | 2時間10分 |
| 1分 | 指定優先（掲載順） | 45分 | 50分 | 4時間7分 | 4時間57分 |
| 6時間 | OFF・確認時に手動 | 2.5日 | 3日 | 12時間 | 3.5日 |
| 6時間 | ON・各3方針 | 1.75日 | 2日 | 6時間 | 2.25日 |
| 12時間 | OFF・確認時に手動 | 5日 | 6日 | 24時間 | 7日 |
| 12時間 | ON・各3方針 | 3.5日 | 4日 | 12時間 | 4.5日 |

初回1e6は未取得なので従来通り、1分確認12分・6時間復帰12時間・12時間復帰24時間です。指定優先は優先順で結果が変わり、掲載順では1分方策で遅くなるため、収穫効率を初期値にしました。自動購入が常に最適、確認頻度が高いほど常に速いとは主張しません。

別途、取得済み・同じ開始状態を使う24ケース（2段階×3確認間隔×OFF/3方針）を比較します。OFFは確認時だけ手動、ONは自動購入のみです。1e9の共通開始状態で1分確認ならOFF3時間40分に対し均等90分・収穫効率87分・指定優先247分、6時間確認ならOFF12時間に対し各ON6時間、12時間確認ならOFF24時間に対し各ON12時間でした。上限後は自動で転生・突破せず待機するので、待ち時間自体は残ります。

現行結果は [生成レポート](balance/generated/report.md)・[24ケースCSV](balance/generated/automation.csv)・[購入時系列](balance/generated/automation-timeline.csv)・[12取得経路CSV](balance/generated/automation-journeys.csv)・[比較図](balance/generated/automation.svg) から追試できます。旧15方策・#20の5経路も残しています。

## 検証

`npm run typecheck` / `npm test` / `npm run build`、`npm run simulate` / `npm run simulate:check` を実行します。21成果物の一致をCIでも確認します。3方針・個別設定・優先順・台数境界、24時間の一括/小分け精算と端数保存、上位設備ロック、上限停止、手動操作との重複防止、設定保持、v1〜v6の移行・破損・書込失敗・競合を検証します。

#29の新設備は段階3のみ購入対象です。効率方針は他設備の連携生産も含む総増分で比較します。未発見の2設備は設定・優先順から隠し、発見後の転生では設定を保ったまま現在段階でロックします。v5〜v8の既存フラグ・優先順は検証して保持し、新設備を個別ONで末尾追加します。[設備連携](root-connection.md) を参照してください。

DEPTHは設備購入/SCORE上限までの固定設備区間内で次の地層境界を処理します。掘削研究は手動のみで、購入方針は芋の効率を維持します。SCORE停止後の深度加算はありません。[深度・精算と許容誤差](depth.md) を参照してください。
