# 巨大数の共通API（#27）

`src/core/numbers.ts` が `break_eternity.js` 2.1.3を包む、ゲームの金額・生産量用の数値境界です。通常依存へ正確な版を固定し、同梱の型定義を利用します。[公式README](https://github.com/Patashu/break_eternity.js#readme) と、インストール済みの `dist/index.d.ts` / 実装を確認して採用しました。

#27で共通APIを追加し、#28で `GameState`・計算・v7保存・UI・シミュレーターへ接続しました。移行の互換性と性能は [巨大数移行](number-migration.md)、保存形式は [保存仕様](save.md) を参照してください。1e15の上限追加は #29です。

## 型とAPI

`GameNumber` は非公開のDecimalを持つ不変のクラスです。ラッパーと内部値をfreezeし、内部の可変な `sign/layer/mag` を外へ渡しません。ライブラリをimportする場所はこのモジュールだけにします。

```ts
import { GameNumber, formatScoreProgress, toElapsedSeconds } from './numbers';

const amount = GameNumber.from('1e1000');
const price = amount.multiply('1.2').ceil();
const affordable = amount.compare(price) >= 0; // native numberへ変換しない
const restored = GameNumber.from(price.toString());
const progress = formatScoreProgress(amount, price); // reached: false
const wait = toElapsedSeconds('1e1000', '1e1000', 86_400);
// { kind: 'within-horizon', seconds: 1 }
```

| API | 契約 |
| --- | --- |
| `GameNumber.from(number \| string \| GameNumber)` | 入力を検証・正規化。既存のGameNumberは不変なので共有可能 |
| `readGameNumber(unknown)` / `isValidGameNumberInput(unknown)` | UI・将来の保存入力用の検証境界 / 例外を出さない妥当性確認 |
| `nonNegativeGameNumber(input)` | 金額・生産量の非負制約。一般のGameNumberは負数も表現する |
| `add / subtract / multiply / divide / pow` | 新しい値を返し、入力を変更しない。結果の非有限値も拒否 |
| `compare / equals / min / max` | 表現された値を直接比較。`compare` は -1 / 0 / 1。丸め・許容誤差は混入させない |
| `abs / negate / sign / isZero` | 符号・絶対値・ゼロの操作 |
| `ceil / floor` | **表現された値**の切上げ / 切捨て。高い桁での1単位精度を保証しない |
| `toString()` | 正規化済み成分の往復形式。画面用とは分離 |
| `format(significantDigits = 3)` | 桁区切り / 科学表記 / 層付き表記。桁数は1〜15 |
| `formatScoreProgress(score, cap, digits?)` | 巨大数比較による `reached` と、未到達を誤認させないSCORE/上限ラベル |
| `toFiniteNumber()` | 明示的な近似変換。Infinityと非ゼロ→0のアンダーフローは例外。安全な整数への変換ではない |
| `toElapsedSeconds(amount, rate, horizonSeconds)` | 金額差÷速度を有限の時間枠内でだけnumberへ変換 |
| `approximatelyEqual(a, b, absolute?, relative?)` | テスト・測定用の明示的な許容誤差。購入判定用ではない |

`+` / `-` / `*` / `>` / `Number(value)` といった暗黙の数値変換は例外にします。`String(value)` は往復形式を返します。`JSON.stringify(GameNumber)` も例外とし、v7保存とシミュレーターでは `encodeGameNumbers` による明示的な文字列化を行います。型アサーションで偽造したオブジェクトやDecimal風のJSONも入力として受理しません。

設備所有数、スキル/研究ランク、転生回数、上限段階は今後も非負の安全な整数の `number`、経過秒数は有限・非負の `number`、タイムスタンプは現在の整数/Date範囲内の `number` を基本とします。これらを一律GameNumberへ置き換えません。

## 入力と正規化の規則

入力文字列は最大256文字。空白のtrimや部分一致を行いません。許可するのは次の2形式です。

1. **通常十進数 / 科学表記**：ASCII数字、任意の先頭符号、任意の小数部、任意の `e/E` と符号付き整数指数。`12`、`-0.125`、`.5`、`1.`、`+1E6`、`1e1000`、`1e-1000` は有効です。指数は絶対値 `Number.MAX_SAFE_INTEGER` 以下の整数だけを認めます。通常の長い仮数も近似値へ丸められ、元の全桁を保持する意味ではありません。
2. **正規化成分形式**：`gn1:<sign>:<layer>:<mag>`。例えば1e1000は `gn1:1:1:1000`、その逆数は `gn1:1:1:-1000`、ゼロは `gn1:0:0:0`。この形式は出力と同じ正規形だけを受理し、`20.0`、不要な先頭0、非正規の成分組合せなどを拒否します。`gn1` はAPIの形式識別子であり、セーブ版ではありません。

signは -1/0/1、layerは0〜`Number.MAX_SAFE_INTEGER - 1`の整数、magは有限numberです。成分をライブラリで正規化した後に再検証します。負のゼロはゼロへ統一し、演算で範囲外へ出た場合も例外にします。成分形式の `mag` はIEEE 754の最短往復文字列なので、`from(value.toString()).toString()` は同じ正規形になります。通常の科学表記で再構築して対数を再計算する場合と異なり、保存/復元のたびに成分がずれることを避けます。

`NaN` / `Infinity`、空文字、改行、末尾のゴミ、桁区切り、全角数字、16進数、`1_000`、`1e1.5`、オブジェクト/配列/boolean/bigintを拒否します。ライブラリ独自の `ee20` / `10^^3` / `2^3` / `(e^2)20` は**入力として渡せません**。層付きの演算結果は成分形式で受け渡します。緩いライブラリ文字列パーサーへ到達する前に構文全体と指数を検証します。

number引数は有限値だけです。すでにJSで `1e1000` がInfinityや `1e-1000` が0になった後の情報を復元できません。巨大/極小の定数は文字列で渡してください。`0` を渡された場合は正当なゼロと扱います。

## 精度と価格の方針

break_eternity.jsは、有限精度の符号・層・大きさで巨大な範囲を近似するライブラリです。金融用の任意桁十進固定精度ではありません。層1では対数のdouble精度、層2以降では指数自体の近似精度に制約されます。範囲を広げても有効桁が無制限に増えるわけではありません。

`1e30 + 1` と `1e30` は同じ表現になり、その差は0になります。通常範囲のべき乗は既存価格列との互換のためIEEE-754の `**` を使用し、層付き領域は近似計算です。`ceil` は表現された値を切り上げるため、巨大域で数学的な真値との完全一致を無条件に保証しません。

採用する価格比較の方針は、**正規化された価格をceilし、残高と厳密な `compare` を行う**ことです。不足額にepsilonを足したり、`approximatelyEqual`なら購入できるようにしたりしません。1芋の差が失われた領域での境界判定は表現上の比較であり、厳密な1単位差の保持ではありません。この制約は #28 の価格移行で明示的に評価する必要があります。

テスト/測定用の許容式は `|a-b| <= max(absoluteTolerance, relativeTolerance × max(|a|, |b|))`。既定値は絶対1e-9、相対1e-12です。ゼロ付近の小さい値では絶対差、通常域では絶対/相対の両方、大きい値では相対差を評価します。極小値同士の演算を検証する場合は絶対許容0を指定し、値が0へ消えても成功するテストにしません。層2以降で表現が同一になった差は、このAPIでも復元できません。精度保証の証明ではなく、検証の許容条件です。

相対比較は同符号の小さい絶対値÷大きい絶対値と `1 - relativeTolerance` を比較する同値な形で評価します。層2以降では `最大値 × 小さい許容率` 自体が元の最大値に丸められるため、その積と差を比べるだけでは無関係な巨大数も合格してしまうからです。異符号の非ゼロ同士は相対許容率1以下で不一致とし、絶対許容を満たす場合だけ一致とします。

検証許容と購入可否は分離します。#28の固定v6比較は金額/速度を絶対1e-8・相対1e-11以下で確認し、段階/台数/購入数/ランクは厳密一致です。旧ロジックへepsilonを継ぎ足さず、価格未満の信用補正は撤去しました。[移行検証](number-migration.md) を参照してください。

## 表示の方針

`format` は既定で有効3桁、絶対値0.001以上1e9未満では桁区切り、それ以外の層0/1では科学表記です。例：`1234 → 1,230`、`1e12 → 1E12`、`1e1000 → 1E1000`、`1e-1000 → 1E-1000`。正数の表示は切捨て、負数は絶対値を切り捨てて符号を付けます。極小の非ゼロを通常表示の0に潰しません。

層2/3は `ee20` / `eee20`、層4以上は `(e^4)20` の形にします。これは `10` の指数の層数とmagを表す略記で、負のmagは巨大な数の逆数です。`ee-20` は `10^(-10^20)` の意味です。層表示のmagは正数値を大きくしない方向へ丸め、負のmagではfloor（例：-20.123→-20.2）を使います。高層の短い表示は非常に粗い近似であり、金額の保存や比較に使いません。

仮数計算やnative変換そのものが表示候補を元の絶対値より大きくした場合は、正数に `<`、負数に `>` を付けて境界を明示します。未到達の `999999999999` を `1E12` とは表示しません。

任意の上限では、切捨て同士でも小さいSCOREと上限のラベルが一致する場合があります。`formatScoreProgress(1233.9999, 1234)` は `{ score: '1,230（未到達）', cap: '1,230', reached: false }` を返します。到達判定を表示文字列の一致や丸め後の値から行わず、巨大数の比較から先に決めます。入力段階で失われた差は検出できないため、表現上すでに等しい値まで未到達とは判定できません。

## 秒数変換と自動購入で残る課題

`toElapsedSeconds(非負の金額差, 正の生産速度, 有限・非負のhorizonSeconds)` は、巨大数のまま割算し、時間枠と比較してからnumberへ変換します。

| 結果 | 意味・呼出側の扱い |
| --- | --- |
| `within-horizon` + `seconds` | 時間枠内の有限秒。金額差0なら0秒 |
| `beyond-horizon` | 時間枠を超える、またはnative最大付近の変換が範囲外になる。次の価格イベントを今回の枠に作らない |
| `below-resolution` | 正の時間がnative最小付近以下で、有限の非ゼロ秒として扱えない。0秒や任意のepsilonへ自動置換しない |

1e1000÷1e1000は1秒となり、1e1000÷1e-1000をInfinity、1e-1000÷1e1000を0として返すことはありません。無効な速度・金額・時間枠は例外です。通常の放置枠には86400秒を渡します。native最大/最小では成分への正規化自体の端数も影響するため、変換結果を再検証し、保守的な範囲外結果を返します。

接続後も精度に関して留意する事項：

- 残高と価格を直接比較し、購入できない場合だけ差を秒数へ変換する。価格より不足なのに差/秒数が0へ潰れた場合は、安全停止して0秒ループを避ける。
- 巨大な累計SCOREに小さな毎フレーム収穫を足しても変化しない場合の累積方法。現在のnumberのKahan端数をそのままDecimalへ移すだけでは解決しない。
- `below-resolution`、同時境界、上限優先、無進捗、処理上限をコアで検証する。隠れたepsilonや0秒ループを導入しない。
- 価格のべき乗・割引・ceilと、現行の到達時間/購入台数の一致条件。厳密な整数価格を別に保持する必要性も判断する。
- v7は明示的な成分文字列を採用し、旧v1〜v6からの移行、不正データ保護と入出力確認を実装する。後続で表現を変える際は保存版も一緒に設計する。
- 生産・購入・補償加算、定義の金額、生産効果、シミュレーター、UI/SCORE表示はこの境界を使い、カウント・時間はnumberを維持する。

これらを踏まえて#28は境界での安全停止・有限の補償・v7移行を実装しました。さらに高い層の進行は、個別の誤差評価なしに現在と同じ精度を保証するものではありません。
