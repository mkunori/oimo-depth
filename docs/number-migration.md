# ゲーム全体の巨大数移行（#28）

#27の共通APIへ、ゲーム計算・自動購入・研究・転生・保存・表示・シミュレーターを接続しました。初期1e6、初回突破1e9、研究突破1e12、設備/研究の値と解禁条件は維持します。1e15の上限、設備、研究、上位転生は追加しません。

## 型の境界

| GameNumber | numberを維持 |
| --- | --- |
| 所持芋、累計SCORE、開始支給、上限、設備価格/費用、生産量/速度、研究費用/返金、補償端数 | 台数、スキル/研究ランク、転生回数/ポイント、上限段階、経過秒数、時刻、有限の設定倍率 |

価格指数・加減乗除・min/max・ceil・金額比較は `core/numbers.ts` を通します。Decimalのimportは同モジュールだけです。購入・上限判定はGameNumberの直接比較で、number変換や検証用の誤差比較を使いません。

現在の到達可能な価格列を維持するため、共通APIの `pow` は入力と結果が層0の通常範囲なら従来と同じIEEE-754の `**` を使い、大きい結果はライブラリへ継続します。既存の「価格倍率^所有数→基礎価格→割引→各台ceil」の順を維持し、整数近傍への独自スナップはしません。巨大域では単位差が失われるので、1芋単位の厳密性は保証しません。

numberへ戻す場所は有限時間枠内の秒数、0〜1のゲージ比率、上限付きの表示、グラフのlog10座標です。大きい残高や価格をnumber化してから比較する経路はありません。極小の非ゼロ値は文字列で保持し、表示も0へ潰さず、ゲージ比率だけは描画分解能未満なら0とします。

## 収穫と購入境界

旧 `automationRemainder` と価格への微小な信用補正を分離し、全収穫の `productionRemainder: { score, imo }` に再設計しました。手動/自動・表示/放置で同じ補償加算を使います。

各値に対し、`adjusted = income - debt`、`next = value + adjusted`、`nextDebt = (next - value) - adjusted` をGameNumberで計算します。端数は符号付きの丸め債務/未反映分であり、表示金額へ毎回加えて購入可能額を増やすものではありません。残高を0へ制限した場合にも債務を消さず、次の収穫で相殺します。転生で両方ゼロへ戻します。

端数の絶対値は `max(1, 現上限) × 32 × Number.EPSILON` 以下に制限し、補償を含めたSCOREも0〜上限内だけ受理します。無制限に端数を増やす状態は保存/進行で拒否します。元の数値表現で失われた差まで復元できるわけではありません。

**残高が価格未満なら、経過0秒では購入しません。** 旧版の「数ULP不足なら価格へ引き上げて購入」という補正は撤去しました。正規化された残高が価格と等しければ購入可能で、その補償債務は以後の収穫へ残します。最終時刻の加算で残高が価格へ丸められた場合も、収穫前の不足推計だけで終了せず実残高を再判定します。これにより0.37秒×約23万回と24h一括の境界でも購入数を一致させます。

金額差÷生産速度は共通の `toElapsedSeconds` で時間枠と比較後に変換します。正のイベント時刻が表現分解能未満なら、0秒や任意のepsilonへ置き換えず `NumericProgressError` で停止します。上限到達を購入より先に扱い、転生・突破・研究は引き続き手動です。

## 保存v7

`imo` / `runEarnedScore` / `runStartingImo` と補償端数を、正規化した `gn1:sign:layer:mag` 文字列で保存します。例：0は `gn1:0:0:0`、1e12は `gn1:1:0:1000000000000`、1e1000は `gn1:1:1:1000`。v7の通常数値・非正規文字列・無効値・負金額を拒否し、符号付き端数にも有限範囲を検証します。

v1〜v6は従来の段階/権限/設備/研究/自動設定の補完と検証を経由し、元のnumberをGameNumberへ変換します。v5/v6の端数は同じ符号で引き継ぎます。既存所有数、スキル、研究、全設定、保存時刻を保持します。旧版で価格の安全整数検証に失敗する所有状態は引き続き拒否します。

旧セーブ移行の書込に失敗した場合は元の保存文字列を上書きせず、そのままエクスポートできます。v7の放置精算そのものが安全条件で失敗した場合にも、読込済み状態と元時刻を保持します。成功していない区間の時刻だけを進めたり、部分購入を保存したりしません。通常の書込失敗、破損、複数タブ、24h制限、確認付き入出力と二重精算防止も維持します。

成分文字列の往復は内部表現をそのまま保持します。旧numberからの変換は、現在の通常範囲の整数/金額を保持しますが、極小値や層の正規化が必要な値では対数表現の近似が入ります。値の範囲を広げることと有効桁を増やすことは別で、将来の巨大域でも整数1単位の完全保存を約束しません。

## 移行前後の固定比較

`src/test/fixtures/balance-v6.json` はmain `dcb7254` のv6レポートから切り出した固定値です。CLIの再生成対象にせず、既存の#4基準 `simulation/baseline.ts` も維持しています。テストは601箇所の状態、876個の購入指標、2985個の時間指標と生産量を比較します。

上限段階・台数・購入数/判断数・全スキル/研究ランク・転生回数/ポイントは厳密一致。金額/速度は絶対1e-8または相対1e-11以下、時間は絶対1µsまたは相対1e-11以下です。v6のJSON自体が12有効桁に丸められているため、その記録精度も含めた比較条件です。上限到達済みSCOREはGameNumberとして上限と厳密一致を別途確認します。

## 性能と停止保護

精算は購入イベント駆動で、放置秒数に比例した固定ループにしません。自動購入1024件、精算内部8192イベント、MAX見積もり50000件を安全上限とし、超過/数値の無進捗は例外で候補を破棄します。現行定義の保守的な自動購入上限619は1024未満です。台数・転生回数・ポイントの次の更新も安全整数内に留め、保存不能なカウンターを生成しません。

小さい不変数値、価格、生産量、残高に依存しない自動方針の候補を上限付きでキャッシュします。生産と方針のキーには台数・関連ランクを、方針には上限段階・個別設定も含め、突破や研究・設定変更で古い候補を使いません。価格8192件、他のキャッシュ各4096件までで、プレイ時間とともに無制限に増やしません。

Node24/Windowsで、24自動比較＋18研究比較をウォームアップ後5回ずつ測った24h精算210件は、中央値約1.7ms、95パーセンタイル約9.3ms、最大約15.9ms、最大160自動購入でした。1e1000超の価格から3台を買う見積もりは約0.47msです。端末差やGCによる参考値であり、テストに時間の厳密な上限は置かず、処理件数と進捗条件を検証します。

## 出力と検証

シミュレーションJSONは結果形式v2、JSON/CSVの金額・速度は正規化文字列、秒数/カウンターは従来のnumberです。グラフは巨大数のlog10だけを描画座標へ変換するため、1e1000をInfinityとして失いません。21成果物を `npm run simulate` で再生成し、`simulate:check` で一致を検証します。旧v6レポートの固定テスト基準は更新しません。

v1〜v6、v7の正規形/破損、実在v6研究保存、移行書込失敗、タブ競合、入出力、0.25/0.37秒分割と24h一括、同時上限/購入、1e100/1e1000価格、巨大MAX処理上限、端数上限、カウンター上限をテストします。今後の1e15やさらに高い層では、追加の数値精度/境界評価を行います。
